# new-api 对接指南 — High Tech VPN 节点 → 代理池

> 目标：把 `tools/refresh.py` 产出的节点变成 new-api 能直接使用的 SOCKS5 出站代理。
> 前提：先把本文档与 `docs/PROTOCOL.md` 读完；节点来自第三方厂商基础设施，**是否入生产池由运营方自行决策**（见第 6 节）。

---

## 1. 架构（推荐，改动量最小）

```
                   ┌──────────── 一次性/定时 ────────────┐
 厂商 API ──加密──► │ tools/refresh.py  → out/nodes.json  │
                   │                   out/mihomo.yaml    │
                   └──────────────┬──────────────────────┘
                                  │
                     mihomo（单进程，多 socks listener）
                     vless-0-app → 127.0.0.1:32001
                     vless-2-app → 127.0.0.1:32002
                     ...                       32003..32006
                                  │
                    proxies.txt（每行 socks5://127.0.0.1:32xxx）
                                  │
                        new-api 代理清单（共享出站代理池）
```

**new-api 侧不需要改任何业务代码**：其代理池支持从清单文件加载 `socks5://host:port`
（住宅/本地协议转换层清单），mihomo 的多 listener 正好就是「一条隧道一个端口」的转换层形态。

## 2. 步骤

```bash
# 1) 拉配置 + 出节点（--upstream 用于国内网络拉取；有直连可省）
python tools/refresh.py --out-dir out --base-port 32000 --upstream socks5h://127.0.0.1:10808

# 2) 起隧道（mihomo 单进程，N 个 socks 端口）
mihomo -f out/mihomo.yaml -d out

# 3) 健康检查，只把存活的写进清单
python tools/probe.py --out-dir out --no-start
python tools/export_proxies.py --out-dir out --out proxies.txt   # 见第 3 节（按 probe.json 过滤）
```

`proxies.txt` 形如：

```
# 由 tools/probe.py 结果生成；格式: socks5://host:port
socks5://127.0.0.1:32001
socks5://127.0.0.1:32002
socks5://127.0.0.1:32004
```

把它挂到 new-api 的代理清单配置上（多文件可用逗号分隔，`#` 开头是注释行）。

## 3. 清单生成脚本（10 行，可直接抄）

```python
# tools/export_proxies.py
import json, os, sys
out = sys.argv[sys.argv.index('--out-dir') + 1] if '--out-dir' in sys.argv else 'out'
dst = sys.argv[sys.argv.index('--out') + 1] if '--out' in sys.argv else 'proxies.txt'
ports = json.load(open(os.path.join(out, 'ports.json')))
probe = {r['id']: r for r in json.load(open(os.path.join(out, 'probe.json')))}
lines = ['# generated by export_proxies.py']
for nid, port in ports.items():
    if probe.get(nid, {}).get('alive'):
        lines.append('socks5://127.0.0.1:%d' % port)
open(dst, 'w').write('\n'.join(lines) + '\n')
print(dst, len(lines) - 1, 'proxies')
```

## 4. 四个必须踩对的坑

1. **容器里的 `127.0.0.1` 是容器自己的 loopback**。若 new-api 跑在 Docker：
   ① `mihomo` 的 listener 改 `listen: 0.0.0.0` + new-api 用 `host.docker.internal:32001`（compose 加
   `extra_hosts: ["host.docker.internal:host-gateway"]`）；
   ② 或 new-api 用 `network_mode: host`；
   ③ 或 mihomo 与 new-api 进同一个 compose 网络，清单里写 `socks5://mihomo:32001`。
   三种任选其一，**否则整池 100% 不可用而面板上看不出原因**。
2. **端口数量决定并发上限**。一条隧道一个端口，6 个节点就是 6 条并发通道；new-api 侧如果按连接轮转，
   单端口在高并发下会排队（QUIC 多路复用能缓解，但别指望单端口扛全站流量）。
3. **住宅/本地清单不做真实出口拨测**。这类来源在 new-api 内通常被标记为高权重且跳过主动测活，
   所以**出口 IP 正确性必须由本仓库的 `probe.py` 负责**（它走 `ip-api.com` 看真实出口），
   不要以为「池里显示可用」= 流量真的走了隧道。
4. **隧道抖动会放大成「整池不可用」**。本厂商的 Cloud Run 中继实测出现过整段 503（见
   `docs/REVERSE_REPORT.md` §5），hysteria2 会同时静默。建议：
   - `probe.py` 每 5–10 分钟一轮，**连续 2 轮失败才摘除**（单轮抖动很常见）；
   - mihomo 常驻，`refresh.py` 每小时一轮做 diff（厂商会滚动改配置，实测 `1.01 → 1.11`）。

## 5. 验收三层（缺一层就等于没验证）

| 层 | 动作 | 通过标准 |
|---|---|---|
| 隧道层 | `curl --socks5-hostname 127.0.0.1:32001 http://ip-api.com/json` | 返回的 `query` 是目标出口 IP、`countryCode` 符合预期 |
| 池层 | new-api 代理池面板 / 列表接口 | 条目数 = 存活节点数，来源标记正确 |
| **业务层** | 发一次真实模型请求，对比上游侧看到的来源 IP | 上游日志里的来源 IP = 出口 IP（不是本机 IP） |

只有第 3 层通过，才算「流量真的走了这条隧道」。

## 6. 已知限制与合规红线

- 出口全部是**数据中心 IP**（Amazon / G-Core Labs 等），不是住宅 IP。对风控严格的上游（要求住宅 ASN）命中率会低。
- 上游是**第三方商业 VPN 的基础设施**（`strongteam.co` / Telegram `t.me/htechvpn`）。把它的节点灌进自己的生产池
  = 免费用别人的带宽与 IP 信誉，且对方随时可能改密钥/封禁；不建议作为主力池，只适合做「稀缺地区补充/临时兜底」，
  且需自担由此产生的合规与稳定性风险。
- Hysteria2 只监听 UDP：容器/防火墙必须放行 UDP 443，否则节点会被误判为死。
- 所有凭证（VLESS UUID、Hysteria 口令）都会随厂商改版而变，**不要硬编码**，一律走 `refresh.py` 重新拉取。
